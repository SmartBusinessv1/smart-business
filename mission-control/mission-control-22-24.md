The strongest evidence-backed progression across MC22–MC24 is:

`MC22 — finish the historical era completely and convert accumulated judgement into durable institutional memory`

→ `MC23 — strengthen execution with truthful Build Assurance, then optimize CI so assurance improves speed instead of becoming ceremony`

The resulting doctrine is:

> **Historical extraction should end as a durable capability, not as another archive people must repeatedly reread.**

> **Automation should reduce repeated checking while increasing evidentiary quality; automation must not create authority.**

> **Self-improving memory does not mean self-modifying governance.**

These are institutional lessons, not independent governance amendments.

# 2. Mission Control Decision Model Learned Across MC22–MC24

Before starting or advancing a mission, ask:

1. **Is this Product work, operational foundation, governance, documentation, or organizational capability?**
   - Classify it correctly before assigning IDs or lifecycle expectations.
   - Do not force every prerequisite into `SB-P-*`.
   - Do not let a non-Product mission silently redefine Product Truth.

2. **What exact outcome is required before the next Product Mission can safely begin?**
   - A prerequisite must have an explicit completion condition.
   - “Useful foundation exists” is not the same as “foundation is accepted and ready to support SB-P execution.”

3. **What evidence proves the actual claim?**
   - Green CI proves only what the job executes.
   - Local success may mutate a shared test environment even when repository code is read-only.
   - A test target's identity and the complete effects of a historical run are separate evidence questions.

4. **Is the problem a real product defect, a test-isolation defect, a workflow-binding gap, or stale evidence language?**
   - Correct the exact layer that is wrong.
   - Do not reopen product implementation for an administrative evidence defect.

5. **Can the assurance path be made faster without weakening assurance?**
   - Fast checks should run on every PR.
   - Expensive integration checks should run where relevant.
   - Documentation-only changes should not automatically incur production-like integration cost.

6. **Does a proposed learning system preserve authority boundaries?**
   - Candidate learning is not approved learning.
   - Evidence eligibility is not authority.
   - A merged PR is not automatically institutional truth.
   - Confidence is not permission.

7. **Is the source historical, current, canonical, generated, operator-attested, or inferred?**
   - Preserve those distinctions in the data model.
   - Never let summaries become evidence for their own claims.

8. **Can the next Mission Control continue without guessing?**
   - Current SHA, mission status, next action, controlling plan, unresolved risks, and stage boundary must be explicit.

# 3. MC-by-MC Institutional Memory

## MC22 — Historical Closeout, Retrospectives, and Whole-Project Memory

### Situation

The project had already reconstructed Founder-origin history through Ground Zero, NotebookLM, specialist-room extractions, former Mission Control memory, and multiple repository artifacts. The risk was that the historical mission could remain “mostly complete” while important institutional lessons, specialist retrospectives, continuity records, and global product-completion knowledge remained scattered.

### What Mission Control did

Mission Control drove a proper closeout of `SB-DOC-PHASE1-HISTORY-1.0` rather than stopping after the first historical extraction artifact.

The closeout work included:

- Founder Accountability retrospective;
- AI & WhatsApp retrospective;
- Former Mission Control retrospective;
- durable `mission-control-13-21.md` extraction;
- Claude Code retrospective with session evidence;
- Codex retrospective with session evidence;
- final project-wide Mission Control institutional-memory synthesis;
- explicit verification that the historical mission met a complete closeout standard rather than a partial “documents created” standard.

The closeout standard included:

- Questions 1–100 complete;
- feature inventory complete;
- mature Feature Definition Library;
- residual sweep complete;
- Product Completion Register created;
- contradictions classified;
- source-reconciliation needs handed off;
- `SB-P-1.0 → 1.11` continuity complete;
- chronology/registers updated;
- tools/resources/capabilities updated;
- lessons learned complete;
- philosophy/reflection synthesis complete.

### Judgement learned

A historical mission is not complete when documents exist. It is complete when future execution no longer depends on reconstructing the same reasoning again.

The strongest lesson was:

> **Evidence must outlive chat memory. Judgement must become durable enough that a future room can act without guessing.**

### Narrow-correction discipline

Several retrospective PRs required administrative corrections after substantive content review. Mission Control learned to distinguish:

- substantive retrospective content;
- completion-report metadata;
- final-head CI evidence;
- Founder merge boundary.

When only completion metadata was stale, only that file changed. Retrospective content was not reopened unnecessarily.

### Inherit

- Separate content acceptance from merge state.
- Preserve reviewed content when only administrative evidence is wrong.
- Never create recursive “final-head CI” claims by editing the same file after every CI run unless the evidence model is designed for it.
- Use PR conversation / immutable repository evidence when self-referential final-head reporting would create infinite churn.
- A retrospective is for institutional memory, not retroactive authority.
- Historical evidence may explain a decision; it does not reactivate old authority.

## MC23 — Build Assurance, CI Stabilization, and Proportional Automation

### Situation

Before beginning the next real Product Mission, the Founder and Mission Control recognized that the repository lacked a sufficiently strong, truthful automated build-assurance baseline.

The objective was not to add ceremony. The objective was to make future SB-P work safer and faster.

### Build Assurance Foundation

The first non-Product foundation mission created application-level CI for:

- lint;
- typecheck;
- build;
- test.

This immediately surfaced two real conditions:

1. pre-existing lint debt;
2. GitHub Actions could not run the real Supabase-dependent test suite because the approved test environment was not yet wired into CI.

This was a success of the assurance system, not evidence that the product had suddenly failed.

### Evidence correction and incident scoping

A local test run had used real Supabase Auth/database operations through configured test credentials. Early wording overclaimed that no provider/production data was affected.

Mission Control required narrow correction until the claim became truthful:

- repository authoring/build commands could be described as non-provider-mutating;
- the historical local integration-test target initially remained `INSUFFICIENT EVIDENCE`;
- a later narrow read-only incident-scoping step established with high confidence that the configured target was the dedicated `smart-business-test` project, distinct from production;
- the complete effects of the historical run were not overstated beyond the available evidence.

### CI stabilization

Mission Control then authorized a narrow stabilization mission:

- formatting-only lint corrections;
- no semantic warning cleanup without separate judgement;
- test job bound to the existing `smart-business-test` GitHub environment;
- Founder provisioned the required non-production Supabase test secrets;
- real CI then executed the full suite successfully: 28 files / 169 tests.

### Key lesson: assurance must not become a tax on every PR

The first assurance design ran the full Supabase/integration suite on every PR. That created ~3–4 minute delays even for documentation-only changes and exposed a flaky global-count assertion in shared test state.

Mission Control recognized that “run everything everywhere” was safe-looking but operationally clumsy.

The answer was not to weaken testing. It was to separate:

### Fast Gate — every PR

- lint;
- typecheck;
- build;
- 8 environment-independent Fast Test files / 61 tests;
- no Supabase secret dependency.

### Full Assurance — selective

- 20 Supabase-dependent files / 108 tests;
- `smart-business-test` environment;
- relevant path triggers + manual dispatch;
- real HTTP, RLS, auth, inventory, catalog-import and integration behavior.

Combined baseline remained:

`28 files / 169 tests`.

### Test-isolation lesson

A security test used an unscoped global row count to prove that a rejected-auth request created no batch. In a shared mutable test environment, another concurrent operation could change that global count.

The correction replaced global-count comparison with a request-specific unique marker and existence check.

General principle:

> **Assert on the object/event owned by the test, not on global shared state, unless global state is the property being tested.**

### CI architecture lesson

A mature assurance system should optimize both confidence and flow:

- fast, deterministic checks on every change;
- expensive environment-dependent checks when relevant;
- full integration assurance before acceptance of affected work;
- no claim that a skipped job “passed”;
- no forcing irrelevant heavy checks onto administrative PRs.

### Communication lifecycle lesson

Mission closeout was not considered complete until:

1. final live instruction/report were archived byte-identically;
2. a reconciled `communication.md` archive record existed;
3. durable mission README/handover status was closed;
4. `communication/live/instruction.md` and `communication/live/report.md` were reset to canonical idle templates.

This became an important operational doctrine:

> **Closing the work and closing the communication lifecycle are both required.**

### Inherit

- Treat CI as evidence infrastructure, not a ritual.
- Keep Fast Gate fast.
- Keep Full Assurance meaningful.
- Never weaken tests merely to obtain green CI.
- Distinguish test-environment failure from product failure.
- Distinguish workflow binding from secret provisioning.
- Use narrow read-only incident scoping when uncertainty is material but broad mutation is unnecessary.
- Archive/reset live communication at mission closeout.

## MC24 — Organizational Learning Engine: From Historical Extraction to Continuous Learning

### Situation

After the historical mission, the Founder identified the next institutional problem:

Smart Business had learned an enormous amount from:

- Founder-origin ideation;
- Ground Zero;
- NotebookLM recovery;
- MC1–MC21 institutional extraction;
- specialist retrospectives;
- Claude Code and Codex retrospectives;
- Build Assurance and CI missions;
- implementation, verification, correction, and handover work.

But without a persistent learning engine, future teams would periodically need to pause execution and repeat manual extraction.

### Founder requirement

The target became:

`completed authoritative mission`

→ `evidence harvested`

→ `candidate lessons extracted`

→ `resources / skills / capabilities / tools observations updated over time`

→ `provenance retained`

→ `confidence / maturity / freshness recorded`

→ `future Mission Control and builders inherit relevant learning`.

The system must improve organizational memory in the background while preserving the constitutional boundary:

> **Self-improving memory does not mean self-modifying governance.**

### Design process

Mission Control did not implement immediately.

It first created `SB-ORG-LEARNING-1.0` as a research/design mission and required a sequential review chain:

`Mission Control proposal → Claude Code engineering review → Mission Control reconciliation → Codex independent/adversarial review → Mission Control final reconciliation → Founder merge`.

This sequence mattered because Claude Code and Codex were assigned different review purposes:

- Claude Code: repository fit, engineering simplicity, implementation realism;
- Codex: adversarial assurance, provenance, authority laundering, security, idempotency, failure modes.

### Engineering simplification accepted

Claude Code correctly challenged overbuilding in the first proposal.

Mission Control accepted a narrower v1 direction:

- repository-native;
- existing Zod/runtime TypeScript conventions;
- Node.js ESM deterministic scripts;
- start with lessons + risks rather than seven dedicated registries;
- prove behavior against one real closed mission;
- keep manual/supervised extraction as a proof-stage step before background automation.

Mission Control preserved one important Founder requirement that could not be optimized away:

> The mature system must eventually perform automatic background candidate learning after authoritative mission closure.

Manual proof is a staging mechanism, not the final product of this organizational mission.

### Adversarial corrections accepted

Codex identified several design risks that were incorporated into the final controlling build plan.

The resulting design requires:

1. generated candidate content cannot self-promote or claim review authority;
2. provenance binds claims to exact evidence, not merely to a file name;
3. source-path allowlisting means eligible-to-read, not authoritative;
4. retrieval respects maturity, freshness, supersession, contradictions and unresolved risks;
5. screening, extraction and publication are isolated and fail closed;
6. background eligibility depends on a versioned authoritative closure envelope, not prose/status heuristics;
7. source snapshot, processing run, candidate revision, human review/promotion and publication identities remain distinct;
8. idempotency, concurrency, atomic publication and recovery are explicit;
9. `communication/live/**` is excluded from authoritative harvesting;
10. automated processing stops at candidate learning and never gains merge/governance/Product Truth/deployment/Product Mission authority.

### Approved first implementation slice

The accepted first implementation slice includes:

- candidate schema;
- promotion/review schema;
- closure-envelope schema;
- processing receipt schema;
- claim-level provenance;
- source allowlist;
- safe path normalization;
- committed-Git-object reader;
- screening/quarantine contract;
- deterministic evidence manifest and source fingerprint;
- Node.js ESM harvester;
- lessons + risks registries;
- Mission Learning Report;
- mission-start context pack;
- freshness, contradiction and supersession handling;
- tests for unsafe paths, prohibited authority fields, invalid provenance, scanner failure, idempotency and recovery.

### Mission sequencing decision

The Founder explicitly decided that the Organizational Learning Engine should be implemented **before `SB-P-1.12`**.

Reason:

The project had just finished reconstructing institutional knowledge at great cost. Starting the next long Product Mission sequence without first making learning continuity durable would recreate the same organizational risk.

Therefore:

`SB-ORG-LEARNING-1.1 — implementation`

is a prerequisite workstream before:

`SB-P-1.12 — Authority, Identity & Product Surface Foundation`.

### Inherit

- Organizational learning is a capability, not governance authority.
- AI-generated learning starts as candidate state.
- Human promotion is a separate write path.
- Founder approval is required for organization-wide institutionalization in v1.
- Evidence must be claim-level and pinned to source identity.
- Generated learning cannot cite itself as primary evidence.
- Current governance loads separately from institutional memory.
- Candidate extraction must be isolated from merge, deployment, production and governance authority.
- Background processing is a required mature outcome, but only after manual proof and deterministic controls work.
- `SB-P-1.12` remains blocked until OLE implementation is accepted.

# 4. Process Improvements Established in This Era

## 4.1 Narrow correction over mission restart

When a defect is confined to:

- one completion report;
- one unsupported evidence claim;
- one test assertion;
- one workflow binding;
- one communication lifecycle gap;

correct that exact defect.

Do not reopen unrelated accepted work.

## 4.2 Current-head verification

After every correction that changes a branch head:

- treat prior CI as evidence for the prior head;
- verify the new head separately;
- do not claim stale CI as final-head proof.

## 4.3 Separate substantive acceptance from Founder merge

Mission Control may complete substantive review while the final protected-main merge remains a Founder/human action.

This allows precise status language such as:

`content review complete — merge pending`.

## 4.4 Separate mission success from product success

A build-assurance mission can succeed by revealing failures.

A CI architecture mission can succeed even when it records non-blocking maintenance debt.

Success means the mission achieved its authorized objective truthfully, not that every observed system condition is perfect.

## 4.5 Close communication deliberately

At mission closeout:

- preserve final live instruction/report;
- create durable archive/reconciliation;
- reset live channel;
- do not leave stale mission instructions active.

# 6. Failure Patterns to Avoid

Future Mission Control should explicitly avoid:

1. running every expensive test on every trivial PR;
2. treating an integration-environment failure as proof the product build failed;
3. using global shared-state counts when request-specific assertions are available;
4. claiming “no mutation” when the executed test path authenticates or writes to a real test backend;
5. treating a test project hostname as proof of every historical side effect;
6. treating path allowlisting as evidence authority;
7. treating AI confidence as promotion authority;
8. treating PR merge as institutionalization;
9. allowing generated lessons to become evidence for themselves;
10. using `communication/live/**` as authoritative historical evidence;
11. leaving stale live instructions after mission closeout;
12. allowing a proof-stage manual process to quietly become the permanent architecture when the Founder approved background automation;
13. allowing background automation to gain governance, merge, deployment or Product Mission authority;
14. starting `SB-P-1.12` before the Founder-approved OLE prerequisite is accepted.

# 8. Closing Institutional Principle

MC22–MC24 converted a difficult historical recovery into a clearer operating philosophy:

> **Do not rely on future people remembering what the organization learned. Build systems that preserve the evidence, carry the judgement forward, and still leave authority with humans.**

The purpose of organizational memory is not to make decisions automatically.

It is to help future humans make better decisions with less repeated reconstruction, stronger evidence, clearer provenance, and fewer avoidable mistakes.
