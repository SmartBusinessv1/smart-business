# Smart Business — Phase 1 Product Mission Operating Pattern

**Document:** SB-P Phase 1 Operating Pattern  
**Scope:** SB-P-1.12 through SB-P-1.20  
**Authority basis:** Founder operating direction, applied through Mission Control under the existing Source 18 lifecycle  
**Status:** Founder-approved operating pattern — becomes canonical only after human merge  
**Purpose:** Preserve the temporary Phase 1 sequencing model created during the GitHub/provider-access incident so successor Mission Control rooms do not confuse documentary readiness with implementation completion.

---

## 1. Why this operating pattern exists

During SB-P-1.12, the Smart Business GitHub account became restricted/flagged. The incident materially affected implementation readiness because important execution and administration surfaces depended on GitHub-linked authentication, including:

- Lovable, the principal application builder route;
- Supabase, the backend administration route;
- GitHub Actions / normal repository assurance paths.

Provider-recovery and continuity work was started. However, freezing all later Phase 1 product-definition work would not reduce the provider risk and would create unnecessary delay.

The Founder therefore directed a parallel Phase 1 documentary/readiness lane:

`SB-P-1.12 → SB-P-1.13 → SB-P-1.14 → SB-P-1.15 → SB-P-1.16 → SB-P-1.17 → SB-P-1.18 → SB-P-1.19 → SB-P-1.20`

The intent is to complete as much Product Mission definition, EIS and implementation-package readiness as can be completed truthfully while implementation access is impaired, then return later to implementation from the exact preserved boundary.

This is a sequencing strategy. It is not permission to claim that suspended upstream runtime behaviour already exists.

---

## 2. Standard temporary Phase 1 pattern

For each Product Mission in the accelerated lane, Mission Control should normally proceed through the documentary/readiness lifecycle until the following boundary is reached:

1. Product Blueprint reviewed and **APPROVED — LOCKED**.
2. EIS reviewed and **APPROVED — LOCKED**.
3. Stage 12 Initial Implementation Package created.
4. Stage 13 Implementation Package Review completed.
5. Implementation Package **APPROVED — LOCKED**.
6. Separate Source 18 Implementation Authorization disposition recorded.
7. If implementation cannot yet be safely authorized, record:
   - **Implementation Authorization: WITHHELD**;
   - **IMPLEMENTATION NOT AUTHORIZED**.
8. Create the mission's documentary/readiness suspension transition:
   - Documentation & Execution-Readiness Completion Checkpoint;
   - Partial Completion and Suspension Report;
   - Residual Work & Exact Resume Register;
   - Communication Suspension and Archive Deferment Record;
   - Partial Mission Learning / OLE Handoff.
9. Suspend the active mission communication cycle without claiming formal mission closure.
10. Move to the next SB-P mission in sequence, after human merge and Mission Control post-merge verification.

The shorthand for the operating pattern is:

**Blueprint locked → EIS locked → Stage 13 package locked → Implementation Authorization WITHHELD → partial completion/suspension → communication cycle suspended → partial OLE handoff → next SB-P mission.**

## 3. Precedent already established

### SB-P-1.12

SB-P-1.12 reached the Stage 13 implementation-package boundary with:

- Product Blueprint locked;
- EIS locked;
- implementation package locked;
- separate Implementation Authorization recorded as **WITHHELD**.

Mission Control then recorded:

**PARTIAL COMPLETION — DOCUMENTATION / EXECUTION-READINESS COMPLETE — IMPLEMENTATION SUSPENDED**

The mission was not formally completed. Stage 23 was not reached. Stage 24 was not reached. The communication cycle was suspended, formal archive was deferred, and a partial OLE learning handoff was created.

SB-P-1.13 documentary/readiness work then began.

### SB-P-1.13

SB-P-1.13 followed the same operating pattern:

- Product Blueprint locked;
- EIS locked;
- Stage 13 Implementation Package **APPROVED — LOCKED v1.0**;
- separate Implementation Authorization recorded as **WITHHELD / IMPLEMENTATION NOT AUTHORIZED**;
- documentary/readiness completion checkpoint recorded;
- partial completion/suspension recorded;
- exact resume point preserved;
- communication cycle suspended and formal archive deferred;
- partial OLE learning handoff created.

SB-P-1.14 then became the next active documentary/readiness Product Mission.

These two missions establish the current Phase 1 precedent.

---

## 4. What "suspended" means

Suspension at this boundary means the product-definition and implementation-package work that can be completed truthfully is preserved, while implementation-dependent work remains open.

It does **not** mean:

- implementation complete;
- runtime verification complete;
- independent verification complete;
- migration execution authorized;
- provider activation authorized;
- production mutation authorized;
- delivery/publication authorized;
- Stage 23 Mission Control acceptance reached;
- Stage 24 documentation closure reached;
- formal mission archive completed;
- formal closed-mission OLE envelope completed.

A suspended mission remains an open Product Mission with a preserved exact resume point.

---

## 5. Implementation work that normally remains deferred

While Implementation Authorization is WITHHELD, later lifecycle work remains pending, including where applicable:

- conditional Stage 14 Founder Lovable Brief;
- Stage 15 implementation;
- Stage 16 Builder Completion Report;
- Stage 17 Human Runtime Verification;
- Stage 18 Mission Control Runtime Review;
- Stage 19 Independent Verification;
- Stage 20 corrective cycles;
- later evidence, reconciliation, completion and acceptance work;
- Stage 23 Mission Control Acceptance;
- Stage 24 formal documentation closure and archive.

No AI actor may use this operating pattern to bypass those stages.

---

## 6. Upstream dependency rule

Later missions may consume locked upstream Product Truth, Blueprint and EIS artifacts as **specifications**.

They must not convert those specifications into claims that upstream runtime behaviour is already implemented.

Examples:

- SB-P-1.13 may specify behaviour that depends on SB-P-1.12 authority rules, while carrying the implementation dependency explicitly.
- SB-P-1.14 may specify Business Memory, UDI and durable-media behaviour that consumes SB-P-1.12 and SB-P-1.13 contracts, while preserving D12/D13/DTX or equivalent holds.
- Later missions must preserve all dependency and evidence holds until actual implementation and verification exist.

A documented dependency is not an implemented dependency.

---

## 7. When this pattern must stop earlier

Stage 13 is a target documentary/readiness boundary, not an obligation to force every mission there.

Mission Control must stop earlier and escalate when a mission cannot be specified truthfully without missing implementation/runtime evidence.

Examples include:

- a genuine Product Truth decision is required;
- a T2/T3/T6/T7/T8 trigger requires Founder or specialist disposition;
- a dependency cannot be represented safely as a hold;
- provider capability is necessary to determine product behaviour rather than merely implementation mechanism;
- legal/privacy/retention uncertainty affects Product Truth or safe specification;
- architecture feasibility cannot be established without evidence;
- continuing would require pretending an upstream runtime capability already exists.

The rule is:

**Accelerate documentation only where truth can be preserved. Never accelerate fiction.**

---

## 8. Implementation Authorization remains a separate gate

Package approval does not authorize implementation.

For every mission, the Source 18 Implementation Authorization remains a separate decision.

If the required builder assignments, branch/path boundaries, environments, assurance baseline, verification plan, runtime-verification plan, migration dependencies, provider evidence or upstream implementation conditions cannot yet be fixed truthfully, Mission Control should record the Implementation Authorization as:

**WITHHELD — IMPLEMENTATION NOT AUTHORIZED**

The missing execution conditions should be recorded as exact future activation prerequisites.

This operating pattern must never be interpreted as automatic authorization to build after Stage 13.

---

## 9. Communication and OLE handling during suspension

When a mission reaches the temporary suspension boundary:

- preserve the active live communication state into the durable mission record;
- suspend the active communication cycle;
- release the reusable live communication base pair only after durable preservation;
- do not fabricate missing historical communication reports;
- defer formal archive until true Stage 24 closure;
- create a partial mission learning / OLE handoff for later missions;
- clearly state that the formal closed-mission OLE envelope is not yet created.

Preferred wording:

**COMMUNICATION SUSPENDED — FORMAL ARCHIVE DEFERRED**

and

**FORMAL OLE CLOSURE ENVELOPE NOT CREATED — MISSION NOT FORMALLY CLOSED**

---

## 10. Resume rule after provider recovery

When GitHub, Lovable, Supabase and any other required execution surfaces are recovered and the relevant conditions are verified, suspended missions should resume from their recorded implementation/readiness boundary.

Do not restart:

- Stage 1 truth intake;
- Blueprint drafting;
- EIS drafting;
- Stage 12 package creation;
- Stage 13 package review;

unless a real post-suspension Product Truth, source, architecture or repository delta requires governed reconciliation.

Before implementation resumes, Mission Control should:

1. read the mission's Partial Completion and Suspension Report;
2. read its Residual Work & Exact Resume Register;
3. refresh only facts that can materially drift;
4. reconcile any post-suspension source/repository changes;
5. verify provider and administrative recovery relevant to that mission;
6. reconsider the separate Implementation Authorization;
7. establish builder, branch/path, environment, CI/assurance, verification and migration prerequisites;
8. continue from the first actually authorized implementation/runtime stage.

The intended future implementation order remains governed mission by mission. Documentary completion across SB-P-1.12 to SB-P-1.20 does not itself authorize a bulk implementation launch.

---

## 11. Recovery and continuity remain parallel work

The documentary/readiness lane does not replace provider recovery.

GitHub, Supabase, Lovable and other administrative recovery/continuity work may continue in parallel.

Runtime availability and administrative recoverability must remain separate truths. A production service continuing to run does not prove that safe administration, migration, rollback or verification access exists.

Provider recovery evidence should be treated as delta evidence. Stable facts should not be repeatedly rediscovered unless freshness is material to the next action.

---

## 12. Mission Control operating checklist

Before moving from one accelerated Product Mission to the next, Mission Control should confirm:

- Blueprint is canonical and locked;
- EIS is canonical and locked;
- Stage 13 package is canonical and locked;
- separate Implementation Authorization disposition exists;
- if withheld, exact activation prerequisites are recorded;
- all upstream/dependency/provider/evidence holds remain explicit;
- no implementation/runtime completion is claimed;
- partial completion/suspension record exists;
- exact resume register exists;
- communication cycle is suspended without false archive;
- partial OLE handoff exists;
- human merge and post-merge verification are complete;
- the next mission's canonical state is inspected before new work is authorized.

---

## 13. Authority boundary

This document records the Founder-approved **Phase 1 operating pattern** for the current provider-recovery period.

It does not amend or replace:

- the Lighthouse Constitution;
- Smart Business Product Truth;
- Source 18;
- locked Product Blueprints;
- locked EIS documents;
- FCTMs;
- Founder Product Decision Records;
- mission-specific Implementation Authorization records.

Where a higher-authority source or a mission-specific Founder/Mission Control decision conflicts with this operating pattern, the higher authority controls.

Mission Control remains responsible for lifecycle sequencing, review, authorization, suspension and acceptance. The Founder remains the authority for Founder-reserved decisions and human merge. AI actors do not self-merge or convert readiness into execution authority.

---

## 14. Standing Phase 1 instruction

Until the Founder changes this operating direction or provider/execution recovery materially changes the plan:

**For SB-P-1.12 through SB-P-1.20, continue one Product Mission at a time through the highest documentary/readiness stage that can be completed truthfully. Where Stage 13 package lock is reached but implementation cannot yet be safely authorized, record Implementation Authorization as WITHHELD, preserve the exact resume point, suspend the communication cycle, extract partial OLE learning, and proceed to the next Product Mission. Do not claim implementation, runtime evidence, formal acceptance or formal closure.**

When the required execution environment is recovered, return to the suspended missions from their preserved implementation boundaries and continue the Source 18 lifecycle under fresh Mission Control authorization.
