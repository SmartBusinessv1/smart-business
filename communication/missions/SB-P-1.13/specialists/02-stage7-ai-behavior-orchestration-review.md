## AI-S7-01 — Untrusted content needs an explicit instruction/data separation contract

**Severity:** High

**Area:** Prompt injection / tool injection / untrusted retrieved content

**Blueprint sections:** §8.3, §8.4, §8.5, §8.8, §8.9, §10.2

**Affected FCTM rows:**  
`24-§10-1`, `24-§10-8`, `24-§11-10`, `24-§20-1`, `24-§22-1`, `24-§25-1`, `24-§25-5`, `24-§31-4`, `22-§24-2`, `10-§23-10`, `BP-§10.2-W7`

**Source / FPDR references:** Contract 24 §10, §11, §20, §22, §25; Contract 22 §24; FPDR-1

**Repository evidence:**  
The Blueprint correctly states that model output cannot widen access, and permission context comes from SB-P-1.12. Contract 24 also rejects permission decisions based only on prompts. However, the current design does not yet define a sufficiently explicit instruction/data boundary for merchant messages, retrieved documents, FAQ content, future WhatsApp content and other externally supplied material.

**Finding:**  
Server-side authorization prevents classic privilege escalation, but prompt injection can still cause harmful behavior **within** an actor's legitimate authority—for example, manipulating a model into selecting an unrelated write tool, over-retrieving sensitive but technically accessible context, or treating text embedded in a receipt/document as system instructions.

Permission checks alone therefore do not close the injection problem.

**Why it matters to merchant dignity / safety / correctness:**  
A merchant should never cause an unintended financial or operational action merely because hostile or irrelevant text appeared inside a document, FAQ result or incoming message. Natural language must remain input, not authority.

**Recommendation:**  
The EIS should establish an explicit untrusted-content contract:

- system/developer policy and tool registry instructions are control data;
- merchant text, documents, retrieved business content, FAQ text and future WhatsApp payload content are untrusted data;
- retrieved content cannot enable tools or alter capability requirements;
- only the application-controlled registry determines which tools are available;
- context retrieval is permission-filtered before model exposure;
- embedded instructions in documents are treated as content, not executable instruction;
- consequential tool selection remains constrained to the recognized intent and capability envelope;
- red-team tests include multilingual and document-borne prompt injection.

**Product-behavior effect:** NONE

**Engineering Review dependency:** HOLD AFFECTED FINDING

**Provider evidence state:** NOT APPLICABLE

## AI-S7-02 — Confirmation must consume the frozen reviewed proposal, not re-run model interpretation

**Severity:** High

**Area:** Clarification / preview / confirmation binding

**Blueprint sections:** §8.5, §10.1, §10.2

**Affected FCTM rows:**  
`24-§11-6`, `24-§20-1` through `24-§20-10`, `24-§21-1`, `24-§21-2`, `24-§21-8`, `24-§21-9`, `24-§21-10`, `24-§31-7`, `10-§7-2` through `10-§7-5`, `10-§17-8`, `10-§23-8`, `BP-§6.2-1`, `BP-§6.2-2`, `BP-§10.2-SA1`

**Source / FPDR references:** Contract 24 §11, §20, §21; Contract 22 §13; SB-P-1.12 EIS-CNF-01/-02; FPDR-1

**Repository evidence:**  
SB-P-1.12 EIS provides a strong single-use `confirmation_bindings` design keyed to actor, business, action, target, fingerprint and authority epochs. SB-P-1.13 says consequential intent follows preview and bound confirmation.

**Finding:**  
SB-P-1.13 must explicitly prohibit a second model interpretation from changing the action after the merchant confirms.

The safe sequence is:

model proposes → server canonicalizes/validates → preview is generated from that canonical proposal → proposal is fingerprinted/bound → user confirms → deterministic command consumes exactly that bound proposal.

A fresh model call after “Yes” must not be allowed to regenerate the amount, party, action, payment method, target or other material field.

**Why it matters:**  
Otherwise a merchant may approve one transaction and the system could execute a semantically different one, despite technically having a confirmation token.

**Recommendation:**  
Make the post-preview proposal immutable. Any material difference requires a new preview and new confirmation binding. Confirmation consumes canonical structured data, never free text such as a generic “Yes”.

## AI-S7-03 — Unknown domain-command outcome must be a first-class state

**Severity:** High

**Area:** Unknown outcome / retries / idempotency

**Blueprint sections:** §8.5, §8.10

Catalog command migrations also contain payload-fingerprint/idempotency patterns.

**Finding:**  
A provider/server timeout after a domain command may occur after the write committed. Treating transport failure as business failure can cause a duplicate retry; treating it as success can create false confirmation.

Every consequential conversational command should have:

- a payload fingerprint;
- a persisted committed outcome;
- an outcome lookup endpoint/path;
- explicit `unknown/pending`, `completed`, and `rejected` handling;
- retry using the same key for the same semantic submission;
- no automatic creation of a new key merely because transport failed;
- text and voice repetitions handled through the same discipline.

# 10. Merchant Dignity and Lighthouse Assessment

The reviewed architecture generally protects the Lighthouse principles when interpreted strictly:

- the AI proposes; Smart Business authority decides;
- the merchant remains owner of consequential decisions;
- employees cannot gain Owner intelligence merely through language;
- uncertainty should produce clarification rather than confident guessing;
- model or provider failure should not become false business truth;
- conversation should reduce friction without replacing structured product capability;
- WhatsApp enhances access without becoming a dependency;
- merchant information should be minimized before provider exposure;
- Malayalam and Manglish must receive equal safety and correctness treatment, not second-class “best effort” semantics.

The most important remaining safety discipline is to prevent convenience from collapsing these separations during implementation.

A model that can technically call a function is not thereby authorized to execute it.

A model that can see data is not thereby entitled to receive all available data.

A user saying “yes” is not authority for a changed action.

A provider returning HTTP success is not evidence that a business command committed.

A prior conversation statement is not authoritative Business Memory.

A channel adapter is not the product kernel.

These principles are consistent with the current Product Truth and should be preserved in the EIS and verification plan.
