## 3. Important Technical Judgements

1. **The proposal's core architecture was independently found to already be *required* by standing governance, not merely permitted.** Round 1 traced the Founder's amendment separating native Conversation from WhatsApp directly to Source 12 §§4–5 ("Single Implementation Rule," "no business workflow shall depend exclusively on WhatsApp") and Source 17 Part B12 ("no core capability shall exist only inside one channel unless Product Truth explicitly requires it") — concluding the proposal was "the correct operationalization of standing governance rather than a new decision," not a novel architectural request needing independent justification.
2. **"Catalog" was found to have zero textual basis anywhere in the 20 canonical governance documents** — not in Source 01's foundation-table list, not in either locked-route list, not in Source 03's Dashboard Architecture, not named in any of the 25 mature contracts. This was a stronger finding than Mission Control's own "product-surface drift" framing: `/catalog`'s top-level nav placement (`src/components/authed-header.tsx`) was never authorized by Product Truth in the first place, which is why this session recommended a Founder Product Decision Record rather than treating the correction as a pure UX/IA judgment call.
3. **The repository's own existing Catalog bulk-import code was identified as materially superior evidence to a document the proposal itself cited.** The proposal's own text referenced "the Lovable opening-stock import" as an example of a preview/confirm architecture defect (an unresolved TOCTOU-style binding problem). Direct inspection found that code does not exist in the canonical repository at all — it lives only in a separate, non-canonical Lovable builder project. What *does* exist canonically, and already solves the exact confirmation-binding problem correctly, is the Catalog product bulk-import feature (`catalog-import.ts`), which persists a `row_idempotency_key` at preview time and reuses it verbatim at commit time. This session recommended generalizing the proven canonical pattern for future UDI work, not the unproven non-canonical one the proposal had assumed was the relevant precedent.
4. **A live, currently-unremediated security residual and a currently-missing CI gate were treated as mandatory pre-acceptance conditions for the *next* mission, not as something this historical-review session should fix.** This required holding two things in tension without collapsing them: naming a real defect precisely (exact migration filename, exact three affected tables) while simultaneously refusing to touch it, since this mission's authority was explicitly documentation/analysis only.

## 4. Mistakes / Weak Assumptions / Corrections

**MISTAKE / FAILURE MODE:** Round 1 recommended splitting several proposed missions into additional Mission IDs (`1.12A/B`, `1.13A/B/C`, `1.18A/B/C`), reasoning from Source 18's 24-stage lifecycle structure that "one Blueprint, one EIS, one implementation package per Mission ID" implied a de facto one-contract-per-mission sizing constraint.
→ **CORRECTION:** Mission Control's `instruction.2.md` explicitly rejected this, citing the Founder's direct request for the minimum sensible number of missions, and directed a second, targeted re-read of Source 18 specifically for controlling language requiring separate Mission IDs. That re-read found none — Source 18 §3's Governing Principles require separating *stages* (definition/engineering/implementation/verification/acceptance) and preventing self-approval, but state no numeric contract-per-Mission-ID limit. The session further recognized that its own cited precedent, `SB-P-1.11` (one Mission ID, ~24 internally staged steps, each independently evidenced), actually *supported* Mission Control's interpretation rather than contradicting it — meaning the original recommendation had cited evidence that, read correctly, argued against its own conclusion.
→ **DURABLE LESSON:** An inference about what a governance document's *structure* implies is not the same as a textual requirement, and must be labeled as inference, not citation, until directly re-checked. When challenged, re-read the specific source for controlling language before defending the original conclusion — and check whether previously-cited evidence was actually read correctly the first time.

**MISTAKE / FAILURE MODE:** Round 1's Catalog verdict recommended obtaining "a Founder Product Decision Record that Product & Price Master is now Source 11 Product Truth" — wording that, on Mission Control's later challenge (`instruction.2.md` §4), risked implying the decision record itself would constitute a Source 11 textual amendment.
→ **CORRECTION:** Round 2 explicitly distinguished three things that must not be conflated: (1) a Founder Product Decision Record (a mission-planning decision), (2) future mission implementation authority (`SB-P-1.12`'s own Source 18 lifecycle), and (3) a constitutional/Source 11 textual amendment (a separate, explicit governance action, not an automatic consequence of either of the first two).
→ **DURABLE LESSON:** When recommending that a governance gap be closed, be precise about which *type* of governance instrument closes it — "the Founder decided X" and "the constitutional text now says X" are not the same event, and casual wording can make the first sound like the second.

**MISTAKE / FAILURE MODE (self-detected, not flagged by Mission Control):** Round 1's Section 9 (Schema/API/Service Evolution Plan) attributed the additive widening of the `transactions` type constraint (to support income/expense/credit/repayment) to `SB-P-1.16`. When round 3 required cross-checking that section against the newly-added Section 8A UX anchors, this session found that 8A.3 correctly expects four-state Ledger recording to be demonstrable by the end of `SB-P-1.14` — and that Contract 3's own maturity requirement and the proposal's own mission table (which separates "mature Ledger/Business Memory foundation" in `1.14` from "3 completion" — the customer-credit-specific layer — in `1.16`) supported `1.14`, not `1.16`, as the correct home for the basic type-widening migration.
→ **CORRECTION:** Round 3 corrected its own Section 9 in place (moving the migration attribution from `1.16` to `1.14`) rather than weakening the Section 8A anchor to match the earlier, incorrect schema plan — explicitly reasoning that the Founder-approved UX anchor was more likely to be correct than this session's own six-week-old (by that point, several rounds old) engineering guess, once the two were found to conflict.
→ **DURABLE LESSON:** When a later cross-check finds a Founder-approved product requirement conflicting with this session's own earlier engineering plan, the default resolution should favor correcting the engineering plan, not quietly reinterpreting or softening the product requirement — and the correction should be made transparently, in place, with the reasoning shown, not silently.

**WEAK ASSUMPTION, DISCLOSED RATHER THAN HIDDEN:** Round 1 could not determine, from repository evidence alone, whether the canonical-repository/production-delivery-repository divergence risk (documented from `SB-OPS-PROD-SYNC-1.0` evidence) should be resolved by formalizing a repeatable sync procedure or by collapsing the two repositories into one.
→ **CORRECTION:** none attempted within this session's own authority — explicitly logged as `[Founder/Mission Control decision required]` in the build plan's Founder Decisions register rather than picking one option and presenting it as settled.
→ **DURABLE LESSON:** An unresolved operational-architecture question that depends on information this session cannot obtain (e.g., organizational preference for repository count, not a technical fact) should be surfaced explicitly as a decision request, not resolved by picking the technically-cleaner-sounding option.
