## 1. Lessons Learned

### 1.1 Architecture

- **`CURRENT — STILL VALID`** Product Master / Inventory / Transaction separation must be held even under pressure to converge tables for engineering convenience. Session-evidence 01 documents this holding under real pressure: Opening Stock was modeled as an Inventory *movement*, never a Catalog field, even though a single combined table would have been the simpler path for that specific bulk-import feature (session-evidence 01, §3 item 1).
- **`CURRENT — STILL VALID`** Native Conversation Workspace and WhatsApp must remain architecturally independent — not because WhatsApp is untrustworthy, but because Source 12 §§4–5 and Source 17 Part B12 already require "no core capability shall exist only inside one channel." This session's own direct work (session-evidence 02, §3 item 1) found this was not a novel Founder request needing independent justification — it was already the mandated shape under standing governance, and the Founder's amendment was the correct operationalization of it, not an exception to it.
- **`CORRECTION / LESSON`** A document a proposal cites as architectural precedent should be verified to actually exist in canonical form before being relied on. This session's direct work found that the Founder-accepted build proposal's own reference to "the Lovable opening-stock import" as an example of an unresolved architecture defect pointed at code that does not exist anywhere in the canonical repository — it exists only in a separate, non-canonical Lovable builder project. What *does* exist canonically, and already solves the cited problem correctly, is the repository's own Catalog bulk-import feature (session-evidence 02, §3 item 3). Citing evidence without verifying it is canonical is a specific, nameable failure mode this session both discovered in someone else's proposal and avoided repeating in its own recommendation.
- **`CAPABILITY PROVEN`** Adapter boundaries can be held under real production pressure, not just in design documents: `SB-OPS-PROD-SYNC-1.0`'s repair work routed every corrective write through the *existing* governed RPC (`create_inventory_movement`), including an administrative production repair, rather than reaching for a raw `INSERT` that would have been faster to write (session-evidence 01, §3 item 5).

### 1.2 Database & Supabase

- **`CURRENT — STILL VALID`** A governed RPC's own guard refusing an obvious fix is evidence that a narrower, explicitly-audited path is required — not evidence the guard should be weakened. `SB-OPS-PROD-SYNC-1.0`'s D-047 dependent-history guard blocked the ordinary unlink/relink repair path for a real production data-integrity defect; the response was a narrower, explicitly-audited administrative side channel, never a relaxation of D-047 itself (session-evidence 01, §3 item 3, §9 item 1).
- **`CURRENT — STILL VALID`** Rehearsal-before-production, with fidelity to the real trigger path, is a named reusable technique: reproduce the exact defect shape in an isolated test project, exercise the fix through the *same* governed RPCs a real session would call (not raw SQL that bypasses business-rule checks), roll back, confirm zero residue, and only then execute against production under its own separate explicit authorization (session-evidence 01, §3 item 5, §9 item 2).
- **`CORRECTION / LESSON`** Before inventing a new lifecycle predicate for a constraint (e.g., "should archived rows be exempt?"), check whether the same table already has an established, documented policy for an analogous column. `SB-OPS-PROD-SYNC-1.0`'s first attempt at a uniqueness-constraint design guessed a status-filtered partial index; the corrected version matched an existing sibling constraint's own documented "archived identities remain reserved" policy exactly (session-evidence 01, §4 item 1).
- **`CORRECTION / LESSON`** `SECURITY DEFINER`/executor-role ownership is a real maintenance obstacle, not a design curiosity — modifying an already-owned governed function required empirically discovering the migration-running role's non-inheriting membership and granting/revoking `WITH INHERIT TRUE` temporarily, verified afterward to leave zero residue (session-evidence 01, §3 item 6). The same theme recurs at smaller scale in `SB-P-1.9`'s `SECURITY DEFINER` → `SECURITY INVOKER` hardening after a Lovable security linter flagged the more privileged mode as unjustified for that function's actual needs (session-evidence 04, §3 item 4, §4 item 2).
- **`CURRENT — STILL VALID`** A completed production migration is never re-executable by policy regardless of file presence, and a diverging environment's own migration *ledger* should be reconciled with the tool's own dedicated repair operation — never by editing the historical migration itself or by fabricating synthetic fixtures to make it appear satisfied elsewhere (session-evidence 01, §2 "Explicitly did not do," §9 item 6; corroborated by `docs/migration/README.md`'s Default-Deny Execution Rule).
- **`MISTAKE / FAILURE MODE` (found and fixed, not this contributor's own defect but directly relevant institutional knowledge)** A PostgreSQL planner limitation folded `SELECT ... FOR UPDATE` combined with a subquery-based RLS `USING` clause to `One-Time Filter: false`, silently breaking an idempotency-replay lookup in `SB-P-1.10`'s `create_inventory_movement()`. Found by a 62-test suite (five real, independently-reproduced failures), root-caused via `EXPLAIN (VERBOSE, COSTS OFF)`, fixed by dropping `FOR UPDATE` and moving the advisory lock earlier. **This is recorded as adjacent institutional knowledge from `SB-P-1.10`, most plausibly a "Claude Engineering" mission per its own bylines, not confirmed Claude Code capability history** — but the lesson is squarely relevant to any future Claude Code work touching idempotency+RLS interactions, so it is preserved here rather than omitted for attribution purity.

### 1.3 Financial Integrity

- **`CURRENT — STILL VALID`** Correction, not destructive edit, is the pattern for fixing a financial record: preserve the original row's identity, write full before/after values plus actor/timestamp/reason to a separate audit table, require the highest applicable authority level, and require explicit confirmation before commit. First established in `SB-P-1.9`'s `correct_transaction()` (session-evidence 04, §2 "Designed/Specified," §3 item 1) and reused as the explicit template for later financial-integrity work (this session's own direct build plan, session-evidence 02, evidence pointer to `00_Founder_Approved_MC_and_CC_Verified_Build_Plan.md`).
- **`CORRECTION / LESSON`** Currency precision (paise, not just whole rupees) is a data-integrity requirement for a financial ledger product, not a display nicety — one of the four real defects an independent Codex review found before `SB-P-1.8`'s acceptance (session-evidence 04, §4 item 3).
- **`CURRENT — STILL VALID`** The four-state Ledger requirement (income/expense/credit/repayment) and customer-credit-specific financial integrity (ageing, balances, warn-not-block, reconciliation) are related but distinct maturity levels of the same Contract 3/Contract 14 — conflating "the transaction type constraint is widened" with "customer credit is mature" is a real sequencing error this session found and corrected in its own prior work (session-evidence 02, §4, third item).

### 1.4 Authentication, Authorization & Permissions

- **`CURRENT — STILL VALID`** Authentication is not authorization, and role is not authority. `SB-OPS-PROD-SYNC-1.0`'s stateless-round-trip correction (session-evidence 01, §4 item 2) is the concrete case: a client-supplied value must be re-verified at the point of mutation even when the server itself produced that value earlier in the same flow — a stateless architecture must not imply a stateless trust boundary.
- **`CURRENT — STILL VALID`** Execution-time permission revalidation, not preview-time trust, is required wherever a consequential action has a gap between proposal and commit. This session's own direct work encoded this as a Founder Runtime Verification scenario for the not-yet-built `SB-P-1.12` (session-evidence 02, evidence pointer to the current build plan's Section 21.3.1 Scenario B: a Manager's permission is revoked mid-workflow, and the pending commit must fail because authority is rechecked at execution time).
- **`CORRECTION / LESSON`** Tool capability does not equal authority, demonstrated concretely, not just stated as policy: `SB-OPS-PROD-SYNC-1.0`'s own session had the *technical* ability to run destructive SQL directly against production at nearly every step, and consistently required a separate explicit instruction for each of six production-execution steps rather than proceeding merely because the mechanism had already been designed and verified (session-evidence 01, §5 "Capability vs. authority, explicitly separated").

### 1.5 Security

This is one of the clearest concrete instances of the theme in the entire reconstructed history.
- **`CURRENT — STILL VALID`** A live security residual identified during a documentation-only review must be named precisely and left untouched, not vaguely described and not silently fixed under the wrong mission's authority. This session's own direct work found and precisely named a residual `anon`-privilege grant on `businesses`, `transactions`, and `transaction_correction_events` (traced to `20260727000000_reconcile_default_grants.sql`, only partially remediated for Inventory by a separate, later mission, `SB-REL-1.10-1.11` Gate 2A-C1) and recorded it as a mandatory `SB-P-1.12` pre-acceptance gate rather than attempting to fix it under `SB-DOC-PHASE1-HISTORY-1.0`'s documentation-only authority (session-evidence 02, §2 "Verified").
- **`UNRESOLVED / NEEDS FOUNDER OR MISSION CONTROL DECISION`** — the exact authorizing instruction and actor for the Gate 2A-C1 `anon`-privilege hardening migration itself was not found preserved in the repository by this session's own research; attribution should not be assumed to be Claude Code, Claude Engineering, or any other specific actor without further evidence.
- **`CURRENT — STILL VALID`** GC-42/GC-43 AWS/IAM/OIDC/Roles-Anywhere evidence collection and correction was performed by **Infrastructure Operations**, not Claude Code — confirmed by this session's own research (no "Claude Code" byline anywhere in the GC-43A/GC-43C evidence packages or the associated CI workflow YAML). Future retrospectives (and this one) must not blur "Claude Code analyzed this infrastructure" with "Claude Code built/secured this infrastructure."

### 1.6 Repository Engineering

- **`CURRENT — STILL VALID`** Canonical repository and production delivery repository are, and have historically been, different truths (`SmartBusinessv1/smart-business` vs. `SmartBusinessv1/starter-supab-shell`), and a canonical GitHub merge alone must never be treated as proof that production contains the accepted application. `SB-OPS-PROD-SYNC-1.0`'s entire existence is evidence this divergence is not hypothetical — the approved `SB-P-1.10`/`SB-P-1.11` application had never actually reached the production delivery repository before that mission corrected it (session-evidence 01 throughout; corroborated by the Infrastructure Operations retrospective's own "two-repository reality" framing).
- **`CURRENT — STILL VALID`** This session's own direct engineering review (session-evidence 02) independently rediscovered and re-flagged the same canonical/delivery divergence risk as a standing, not merely historical, concern for every future `SB-P-*` mission's rollback/compatibility planning — corroborating the Infrastructure Operations room's own conclusion from a different vantage point.
- **`CORRECTION / LESSON`** An inference about what a governance document's *structure* implies is not the same as a textual requirement, and must be re-verified directly when challenged. This session's own direct work initially inferred, from Source 18's stage-separation structure, that missions should be capped near one contract per Mission ID — Mission Control's challenge required a second, targeted re-read that found no such textual limit, and further found that the very precedent this session had cited (`SB-P-1.11`, one Mission ID with ~24 internally staged steps) actually supported the opposite conclusion (session-evidence 02, §4 item 1).

### 1.7 Lovable

- **`CURRENT — STILL VALID`** Builder-produced (Lovable) code is evidence, not canonical completion, and must never be reverse-synced wholesale into canonical — a narrow, explicitly-gated rebase is the only safe promotion path, per the Lovable Builder/Lovable Lab retrospectives' own independently-reached conclusion, corroborated by this session's own direct finding that the non-canonical Lovable opening-stock code should be treated strictly as reusable evidence subject to a 12-point promotion gate, never promoted as-is (session-evidence 02, §3 item 3).
- **`CAPABILITY PROVEN`** A Lovable-side security scan/linter caught two real, independent defects across the reconstructed history: raw Supabase/database error-message leakage in `SB-P-1.7`'s dashboard (session-evidence 03) and an unjustified `SECURITY DEFINER` mode in `SB-P-1.9`'s correction RPC (session-evidence 04) — both corrected before or shortly after their respective mission's own completion report.

### 1.8 Implementation Audit / Product-Definition-vs-Implementation Boundary

- **`CURRENT — STILL VALID`** A mature feature contract's existence is not evidence of its implementation. This session's own direct work adopted this discipline directly from the final-reconciliation audit chain and the 25-contract Global Product Completion View: at the time of its review, no mature contract was proven complete end-to-end, and the strongest existing foundations (auth, business identity, Transactions, Inventory, Catalog/Pricing) were explicitly classified `IMPLEMENTED BUT INCOMPLETE`, not `COMPLETE` (session-evidence 02, evidence pointer to the current build plan's Section 6).
- **`CURRENT — STILL VALID`** "Lambda exists" does not mean "UDI exists," and "a governed RPC exists" does not mean "the feature contract is satisfied" — this session's own direct work independently confirmed the AWS Lambda parser offload path is real and deployed to non-production infrastructure but not yet wired into any merchant-facing UI, and treated it accordingly as `NARROW REBASE REQUIRED`, not `PRESERVE` outright (session-evidence 02, Section 8 of the current build plan).

### 1.9 Product / Engineering Boundary

- **`CURRENT — STILL VALID`** Good engineering review can expose a product question; it must not silently answer one. This session's own direct work is the clearest evidence of this principle actually being followed under real correction pressure: when Mission Control challenged this session's Catalog-verdict wording for implying Source 11 had already been amended, the response was a three-way distinction (Founder Product Decision Record ≠ future mission implementation authority ≠ constitutional/Source 11 textual amendment), not a defense of the original wording (session-evidence 02, §4 item 2).
- **`CURRENT — STILL VALID`** Catalog is preserved and evolved into **Product & Price Master — CORE SHARED FOUNDATION**, never a 26th feature, never deleted. This session's own direct work found the underlying case for this reclassification was actually *stronger* than Mission Control's own "product-surface drift" framing: "Catalog" has zero textual basis anywhere in the 20 canonical governance documents, meaning `/catalog`'s top-level navigation was never authorized by Product Truth in the first place (session-evidence 02, §3 item 2).
- **`CORRECTION / LESSON`** When a later cross-check finds a Founder-approved product requirement conflicting with this session's own earlier engineering plan, correct the engineering plan and show the reasoning — do not quietly reinterpret or soften the product requirement to match the earlier plan. This session's own direct work did exactly this when Section 8A's four-state-Ledger anchor (correctly assigned to `SB-P-1.14`) conflicted with this session's own earlier Section 9 schema attribution (which had misassigned the same migration to `SB-P-1.16`) (session-evidence 02, §4 third item).
- **`CURRENT — STILL VALID`** Opening Stock: preserve the capability; revalidate the mechanism. The non-canonical Lovable opening-stock code's preview/commit binding defect (a TOCTOU-style problem where a Catalog change between preview and commit could silently retarget a write) is real, useful evidence — but the capability itself remains `BUILD NOW`, to be delivered via a narrow rebase onto the canonical repository's own, already-correct `catalog-import.ts` binding pattern, not via direct promotion of the flawed non-canonical code (session-evidence 02, §3 item 3, §12 of the current build plan).

### 1.10 PASS Must Be Narrow / Denial Paths / Idempotency / Unknown-Outcome Semantics

- **`CURRENT — STILL VALID`** A PASS means only what the evidence proves. `SB-P-1.11`'s Stage 19 report is the concrete, doubly-instructive case: 113 checklist items with zero FAILs was explicitly *not* treated as "nothing is wrong" — a distinct Material Finding (production two migrations behind test) and five named FOLLOW-UP items were surfaced despite the clean FAIL count, and the report's own "production correctly configured" claim was itself later found to rest on generalized test-project evidence rather than direct production proof (session-evidence 05, §3 items 1–2, §4).
- **`CURRENT — STILL VALID`** Denial-path verification is a first-class case, not an afterthought. `SB-OPS-PROD-SYNC-1.0`'s Phase A rehearsal explicitly exercised a reuse-rejection path and a cross-business isolation check alongside the normal-link happy path (session-evidence 01, §3 "Verified"); this session's own direct work built this same discipline into every Founder Runtime Verification scenario it authored for the not-yet-built missions, each scenario explicitly naming both an "expected experience" and a "protected/denied behavior" field (session-evidence 02, evidence pointer to the current build plan's Section 21.3).
- **`CURRENT — STILL VALID`** Idempotency is a full concurrency contract, not a unique-key column: `SB-OPS-PROD-SYNC-1.0`'s repair migrations used precondition `RAISE EXCEPTION` guards *and* post-write assertions, so a materially changed runtime state at execution time aborts cleanly rather than partially applying (session-evidence 01, §5). The `SB-P-1.10`-era idempotency defect (adjacent knowledge, not confirmed Claude Code attribution — see §1.2 above) reinforces the same point from the failure side: an idempotency mechanism can look correct in isolation and still fail under a specific planner/RLS interaction that only appears under concurrent replay.
- **`UNRESOLVED`** — no explicit `UNKNOWN_OUTCOME` state (distinct from `FAILED`/`SUCCEEDED`) was found named anywhere in the evidence reviewed for this retrospective. `SB-P-1.11`'s FOLLOW-UP classification is the closest analogue found (a claim genuinely not yet verified, disclosed as such, distinct from both PASS and FAIL) but it applies to verification-item disposition, not to the outcome of a specific committed database operation. Whether a dedicated `UNKNOWN_OUTCOME` semantic exists elsewhere in the codebase was not confirmed by the evidence available to this synthesis — flagged in Section 10, not assumed either way.

### 1.11 UX Anti-Drift

- **`CURRENT — STILL VALID`** A Founder-approved human-experience anchor cannot be weakened for implementation convenience, but a genuine sequencing/measurability defect in *when* an anchor becomes testable can and should be corrected — these are different things, and conflating them in either direction is a failure mode. This session's own direct work corrected exactly two anchors on this basis (an `SB-P-1.12` claim about Ask-CFO denial, testable only once Ask CFO exists in `SB-P-1.15`; a cross-tenant "converse about" claim, testable only once Conversation exists in `SB-P-1.13`) while explicitly carrying the underlying guarantee forward into the correct later mission's own verification, rather than deleting it (session-evidence 02, §4 first two items).
- **`CURRENT — STILL VALID`** The Completion Report Experience Verification Matrix rule (PASS/FAIL/NOT APPLICABLE/DEFERRED BY APPROVED DEPENDENCY, with DEFERRED requiring an explicitly-owned later mission) is technically and governance-sound and was independently assessed as such, not merely accepted because Mission Control proposed it — this session's own direct work checked it against Source 12 Part 2's existing evidence standard before adopting it (session-evidence 02, evidence pointer to the current build plan's Section 21.4).

## 5. Suggestions to Improve This Project

1. **Move the two known `SB-P-1.12` gates (`anon`-privilege remediation, automated CI) to the very first internal workstream**, since both are cheap, block nothing else, and are already independently identified by this contributor, the Claude Engineering retrospective, and the Security & Permissions retrospective as live, not hypothetical.
2. **Adopt an explicit "Executing AI" byline convention on every future mission's stage artifacts**, matching `SB-P-1.11`'s pattern — this retrospective's own need to infer, then correct, actor attribution for `SB-P-1.4`–`SB-P-1.10` is a concrete, avoidable cost that a one-line convention would have prevented.
3. **Reuse the `SB-OPS-PROD-SYNC-1.0` rehearsal-before-production pattern as the named standard** for any future schema or data migration, not as a one-off technique specific to that mission.
4. **Reuse the canonical `catalog-import.ts` preview/commit identity-binding pattern as UDI's reference architecture** (`SB-P-1.14`) rather than the non-canonical Lovable opening-stock code, which this contributor's own direct work found solves the same problem incorrectly.
5. **Keep the Experience Verification Matrix rule's PASS/FAIL/NOT-APPLICABLE/DEFERRED-BY-APPROVED-DEPENDENCY granularity** as the model for all future verification reporting, including non-UX technical verification — `SB-P-1.11` Stage 19's own PASS/FAIL/FOLLOW-UP/NOT-APPLICABLE disposition (plus a separate Material Finding category) is direct precedent that a binary pass/fail is insufficient for a checklist of any real size.
6. **Resolve the canonical-vs-delivery-repository question explicitly** before `SB-P-1.12` schema work begins, rather than continuing to carry it as an unresolved risk across missions — this contributor, Infrastructure Operations, and Claude Engineering have now independently converged on flagging the same risk from three different vantage points, which is itself evidence the risk is real and overdue for a decision.
7. **Require every future mission's verification stage to include at least one denial-path scenario per authority boundary it touches**, not only a happy-path proof — `SB-P-1.11` Stage 19's own follow-up register shows this was *planned for* but not *fully executed* even in one of the more mature missions (`F23-01`, `F23-02`).

## 6. What Future Rooms Must Know Before Touching This Area

1. **Read current Product Truth before touching code.** Start from `00_Founder_Approved_MC_and_CC_Verified_Build_Plan.md`, the relevant mature feature contract(s), and current `main` — not from any historical Claude Code session's own conclusions, including this retrospective's own Section 1.
2. **Verify current `main`'s exact SHA and current mission stage before acting.** Do not infer either from memory or from a prior session's report.
3. **Do not infer authority from tool access.** This retrospective's single clearest evidence for this is `SB-OPS-PROD-SYNC-1.0`'s own explicit statement that it had the technical ability to run destructive SQL directly against production at nearly every step and required a separate explicit instruction for each of six production-execution steps anyway.
4. **Do not treat "Executing AI: Claude" or "Claude Engineering" and "Executing AI: Claude Code" as interchangeable.** They are named as distinct actors in the repository's own artifacts; this retrospective had to correct its own draft evidence files once this was discovered mid-task.
5. **Do not create an EIS before Blueprint lock, or an implementation package before EIS lock.** Source 18's gate order is not optional scaffolding — `SB-P-1.11`'s own stage-numbered artifact chain (through Stage 23) is the concrete precedent for what following it looks like.
6. **Do not accept a Builder Completion Report, or your own prior verification report, as independent proof.** `SB-P-1.11` Stage 19's own correction is the concrete case where a verification report's claim about production had to be independently re-proven with production-specific evidence, not merely re-asserted.
7. **Verify denial paths, not only success paths**, for every authority boundary a change touches.
8. **Preserve financial integrity via correction, not destructive edit** — preserve row identity, log full before/after values, require the highest applicable authority, require explicit confirmation.
9. **Preserve business isolation and audit/history** as first-class requirements, not implementation detail — check RLS/grants directly, never infer isolation from UI behavior alone.
10. **Record unknown state honestly.** If evidence cannot confirm a claim (e.g., "was this migration ever applied to production?"), say so explicitly rather than assuming either way — this retrospective itself does this throughout Section 10 rather than resolving every open item by inference.
11. **Stop when architecture or authority is ambiguous**, and escalate rather than guess — this retrospective's own unresolved items (Section 10) are left unresolved deliberately, not filled in with a plausible guess.
12. **Prefer narrow correction over broad rewrite.** `SB-OPS-PROD-SYNC-1.0`'s entire pattern (six separately-authorized narrow production steps, none inferred from a prior one) is the concrete model.
13. **Reconcile before moving code between repositories**, and never silently overwrite newer canonical work with an older builder/delivery-repo snapshot.
14. **Give Mission Control evidence, not confidence.** Every claim in this retrospective is traced to a specific file, PR, commit, or migration in Section 9 — a future contributor's own retrospective should hold itself to the same standard.
