## 8.1 Stage 10 specialist-review boundary

**Classification:** `CONFIRMED`

## 8.2 B1 physical-enforcement architecture

**Classification:** `CONFIRMED`

The backend review accepted the selected physical-enforcement design around `parser_upload_leases` except for a migration-order blocker.

PASS findings preserved in the transcript included:

- mutation-surface design;
- transition-helper contract;
- six-state database invariants;
- authority-field immutability;
- illegal-transition prevention;
- bounded failure-code contract;
- safety-case matrix.

The room did not reopen already-PASS findings during the later narrow correction cycles.

This is a strong example of **narrow reverification discipline**.

## 8.3 Migration activation ordering blocker

**Classification:** `CONFIRMED`

The room identified that the EIS did not yet bind the activation order tightly enough.

The required sequence was eventually constrained so that:

1. support objects exist but are not yet usable by application paths;
2. state invariants and bounded validation are installed;
3. public/browser-role privileges are neutralized;
4. direct `service_role` DML is removed;
5. only narrow helper execution authority is granted;
6. pre-cutover verification passes;
7. only then may application/server paths use the lifecycle.

This is more than migration sequencing. It records a mature security principle:

> **Enforcement must exist before use becomes possible.**

## 8.4 Additive GRANT mistake caught before cutover

**Classification:** `CONFIRMED`

A later backend confirmation identified a narrower but important flaw:

`GRANT SELECT` alone did not remove inherited/default broader `service_role` privileges.

Because repository default-grant posture could give future public tables broad `service_role` privileges, the correct sequence required:

1. explicit revoke / neutralization of the broader effective privilege;
2. proof that no direct INSERT/UPDATE/DELETE remained;
3. restoration of exactly SELECT;
4. helper EXECUTE grants only afterward;
5. effective-state verification before cutover.

The specialist explicitly rejected source-text reasoning that assumed `GRANT SELECT` narrowed an existing broader grant.

Lesson:

> **Privilege security must be verified from effective state, not inferred from intended migration statements.**

## 8.5 Effective-state verification standard

**Classification:** `CONFIRMED`

The final PASS required later implementation evidence demonstrating actual resulting ACL/privilege behavior, including:

- direct SELECT succeeds;
- direct INSERT denied;
- direct UPDATE denied;
- direct DELETE denied;
- no broader table privilege survives;
- intended helper EXECUTE grants exist;
- no broader function grant remains;
- direct privileged mutation outside helpers fails closed;
- legal helper transition succeeds;
- application cutover remains blocked until all checks pass.

This is a high-value institutional lesson for future database/security work.

## 8.6 Fail-closed partial installation and rollback

**Classification:** `CONFIRMED`

The review required that partial installation must not leave an under-enforced but usable lifecycle.

If a required restriction could not be installed or verified:

- helper grants must not proceed;
- application cutover must not proceed;
- retry/rollback must preserve a fail-closed state.

This becomes a reusable Team LIPS backend-security capability, not merely an SB-P-1.11 parser detail.

# 11. Lessons Learned Register Contribution

## Lesson 1 — Capability can pre-exist authority

**What happened:** Supabase Lab was active as a specialist capability while Phase 1.1 remained owned by Infrastructure and database mutation was locked.

**Learning:** An available specialist room or connected platform does not mean the project is authorized to use it.

**Classification:** Organization-wide capability / governance learning.

## Lesson 2 — Source gaps must remain visible

**What happened:** the surviving Supabase histories skip the original implementation sequence that would be expected for Auth/schema/RLS.

**Learning:** do not infer mission identity from the room name or current architecture; preserve the archival gap.

**Classification:** Historical reconstruction discipline.

## Lesson 3 — Review only the failed control

**What happened:** successive SB-P-1.11 confirmations repeatedly kept already-PASS B1/B2/B3/B4 findings closed while reviewing only the remaining blocker.

**Learning:** narrow reverification protects momentum and prevents unrelated regression of accepted decisions.

**Classification:** Team LIPS execution capability.

## Lesson 4 — Install enforcement before activation

**What happened:** migration-order review required constraints, privilege restrictions and verification before application paths could use the new lifecycle.

**Learning:** cutover order is part of security architecture.

**Classification:** Backend/security architecture capability.

## Lesson 5 — A narrow GRANT is not a revoke

**What happened:** `GRANT SELECT` was correctly recognized as additive when inherited/default broader privileges could already exist.

**Learning:** privilege narrowing requires explicit removal of broader effective authority before granting back the intended minimal set.

**Classification:** Backend/security architecture capability.

## Lesson 6 — Verify effective privileges, not migration intent

**What happened:** the final review required actual ACL/behavior evidence rather than assuming migration source text produced the intended state.

**Learning:** security truth is the resulting effective state.

**Classification:** Organization-wide security/evidence capability.

## Lesson 7 — Partial deployment must fail closed

**What happened:** the EIS review required application use to remain disabled if installation or verification was incomplete.

**Learning:** partial installation must not create a temporarily under-enforced live path.

**Classification:** Production/backend safety capability.
