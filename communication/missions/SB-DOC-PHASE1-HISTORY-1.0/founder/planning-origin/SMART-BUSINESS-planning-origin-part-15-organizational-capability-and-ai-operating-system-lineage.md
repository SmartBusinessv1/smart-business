## 4. Capability memory is not capability entitlement

The planning conversation includes an important balancing rule.

The point is not:

> We did it once, therefore we can always do it ourselves.

The point is:

> Check what we already know and own before paying, outsourcing, or relearning; then evaluate whether that capability is sufficient for the new quality requirement.

This protects both:

- financial / operational sustainability; and
- quality.

## 6. Existing-source awareness as an AI operating rule

When testing the Lighthouse Project Architect against a parent-company website idea, the Founder identifies an inefficiency:

If the Lighthouse Constitution already defines Lighthouse identity and mission, the AI should not ask the Founder to recreate that truth through discovery questions.

The historical correction becomes:

1. read existing authoritative source material;
2. extract the Known Foundation;
3. identify only genuinely unresolved project-specific questions;
4. ask the Founder those questions;
5. avoid repetitive discovery.

This directly anticipates later mature Smart Business rules such as:

- source synchronization;
- repository-first intake;
- read before write;
- do not ask the Founder to resolve what the repository can resolve;
- do not invent missing authority.

The later canonical sources are independently authoritative; Part 15 is provenance for the thinking pattern.

## 7. Discovery and finalization are separate states

The planning-era Architect distinguishes two modes:

### Discovery / Refinement

- understand;
- question;
- challenge respectfully;
- identify opportunities and risks;
- understand current assets;
- understand future direction;
- confirm scope.

### Project Finalization

Only after sufficient Founder approval:

- create durable source files;
- create room activation prompts;
- create roadmap / Mission Control structure;
- create final project report;
- hand the project into execution.

This separation is historically important because later Smart Business governance develops much more formal stage boundaries between discovery, blueprint, engineering, implementation, verification, and acceptance.

## 8. AI workspace context should be responsibility-specific

Part 15's Claude Pro discussion identifies another durable AI-operations principle:

An engineering AI does not necessarily benefit from every company document.

Unrelated context may produce unwanted scope expansion, such as suggesting growth features while the active mission is a narrow transaction workflow.

The historical answer is a focused engineering knowledge stack covering:

- enduring Lighthouse boundaries;
- Smart Business product identity;
- cross-system architecture;
- AI / WhatsApp behavior;
- database / security constraints;
- frontend-builder rules;
- technical build sequence.

This model is later superseded operationally by more rigorous mission-scoped source packs and artifact handovers in current governance.

The surviving principle is:

> **Context should be sufficient, authoritative, and role-relevant.**
