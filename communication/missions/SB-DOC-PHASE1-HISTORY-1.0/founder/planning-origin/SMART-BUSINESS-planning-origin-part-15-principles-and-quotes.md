## 1. Provenance discipline

This file separates:

- `FOUNDER DIRECT` — wording or idea directly supplied by the Founder;
- `FOUNDER DECISION` — explicit Founder direction or accepted operating choice;
- `ASSISTANT SYNTHESIS` — assistant-created wording or framework;

## 2. Organizational memory should compound

### FOUNDER DIRECT / FOUNDER DECISION

The Founder asks for Lighthouse Architect to retain **resources memory and skill memory** so future projects can reuse what Lighthouse already owns and knows.

The practical examples are especially important:

- if Lighthouse already has hosting capacity, do not recommend paying for unnecessary hosting;
- if Canva can satisfy the design need, do not recommend paying for a poster by default;
- if Claude is already available for app work, do not assume a new AI coding tool must be purchased;
- if a previous project taught Lighthouse how to build a WordPress website, the next website project should begin from that accumulated capability rather than from zero.

This is a direct organizational-compounding idea.

### ASSISTANT SYNTHESIS / HISTORICAL CANDIDATE

> **“A real architect should think: We built before. What assets, skills, systems, and knowledge can we reuse?”**

> **“This is how real organizations compound.”**

These formulations are assistant-authored, but they accurately capture the Founder request and are worth preserving for later institutional review.

## 3. Capability memory as a distinct institutional layer

### ASSISTANT SYNTHESIS / HISTORICAL CANDIDATE

The planning dialogue proposes four complementary organizational memory questions:

- Constitution: **Why do we create?**
- Project Architect: **How do we create?**
- Case Study: **What have we created before?**

This is a strong institutional-memory architecture because it separates purpose, method, history, and reusable capability instead of mixing them into one giant file.

The proposed Capability Library categories are:

- infrastructure;
- software/subscriptions;
- skill memory;
- build experience;
- marketing capability;
- partnerships/network;
- lessons learned.

The underlying principle is more important than the exact file layout.

## 4. Do not purchase or outsource reflexively

### ASSISTANT SYNTHESIS / HISTORICAL CANDIDATE

> **“Do not purchase what Lighthouse already owns.”**

> **“Do not outsource what Lighthouse already knows.”**

These are useful but should not be interpreted as anti-investment rules.

The same planning dialogue corrects for that risk by adding:

> **“Do not assume existing capability is enough. Evaluate realistically.”**

and later:

> **“Do not avoid investment when quality requires it.”**

The mature synthesis is therefore:

**reuse before repurchase; reuse before outsourcing; but do not let pride in internal capability reduce quality.**

This strongly aligns with current Smart Business reuse-before-creating and sustainability principles, though those current rules are independently authoritative.

## 7. Discovery before architecture

### FOUNDER DECISION / ACCEPTED DIRECTION

The Founder repeatedly improves the Project Architect so it does not jump from an idea directly into sources, rooms, roadmaps, or execution.

The approved planning behavior becomes:

- understand first;
- converse rather than interrogate;
- improve the idea with the Founder;
- ask only a few useful questions at a time;
- understand the ecosystem and existing assets;
- confirm scope;
- then design the project.

### ASSISTANT SYNTHESIS / HISTORICAL CANDIDATE

> **“Improve clarity before improving execution.”**

> **“A project should become stronger during discovery.”**

These are strong formulations for later review.

They also echo the Lighthouse principle that creation begins by understanding a human need rather than creating change for its own sake.

## 8. Existing truth should reduce unnecessary questioning

### FOUNDER DIRECT / FOUNDER DECISION

During a Lighthouse website test, the Founder challenges the Architect for asking questions already answered by the Lighthouse Constitution.

The Founder explains that the AI should understand Lighthouse as a mission-driven innovation ecosystem from the source rather than force the Founder to restate established identity.

The resulting decision is to distinguish:

- **Permanent Lighthouse principles already defined in sources**;
- **Project-specific decisions still requiring discovery**.

### ASSISTANT SYNTHESIS / HISTORICAL CANDIDATE

> **“Known Foundation vs Unknown Project Decisions.”**

This phrase is particularly worth retaining because it captures a mature AI collaboration rule:

**read what is already known before asking the human to repeat it.**

### CURRENT CANONICAL ECHO

Current Smart Business AI Operations and mission lifecycle governance require source loading and repository-first intake before action, and prohibit using chat memory as a substitute for authoritative artifacts.

## 11. Technical possibility is not enough

### FOUNDER DECISION / ACCEPTED DIRECTION

The Project Architect feasibility framework asks not only whether something can be built, but whether Lighthouse can responsibly create and maintain it.

It evaluates:

- time;
- cost;
- human capacity;
- maintenance;
- risks;
- existing assets;
- legal/compliance needs;
- physical production realities where applicable.

### ASSISTANT SYNTHESIS / HISTORICAL CANDIDATE

> **“Can Lighthouse responsibly create and maintain this?”**

> **“Not only: Can this be built?”**

This is a strong organizational principle candidate.

It directly echoes the current Lighthouse Constitution's product-creation tests around real need, meaningful value, respect, sustainability, and alignment.
