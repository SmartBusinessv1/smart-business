## 1. Root Cause

`bun.lock` retains a stale root-dependency entry for `@lovable.dev/cloud-auth-js@^1.1.2` that was correctly removed from `package.json` (and from `package-lock.json`) during the `SB-MIG-1.2F` production cutover on 27 July 2026, but was never regenerated to match. `bun install --frozen-lockfile` refuses to proceed because the lockfile would need to change to reconcile with the manifest — exactly the condition described in `instruction1.47.md` §2, reproduced verbatim in this investigation (§5 below).

The Zod `prefault` question (§4) is an **unrelated, separate, and — on the evidence gathered — non-issue** in the canonical dependency graph. It does not share a root cause with the lockfile defect.

**Why `package-lock.json` updated but `bun.lock` didn't:** `69deab2`'s tooling only touched `package-lock.json`. `bun.lock`'s package resolution URLs are stamped `europe-west4-npm.pkg.dev/lovable-core-prod/sandbox-npm-cache/...` — Lovable's own sandbox package cache — confirming `bun.lock` is specifically the lockfile Lovable's own build environment consumes and regenerates, while `package-lock.json` is a secondary npm artifact from local/non-Lovable tooling. The cutover commit was made outside Lovable's environment (via `npm`), so it updated `package-lock.json` but had no mechanism to touch `bun.lock`.

## 4. Task C — Zod Compatibility Findings (investigated without changing Zod)

1. **Exact Zod version resolved by the canonical graph:** `package.json` declares `zod: ^3.24.2`; a fresh, correct lockfile resolution (§5) resolves the top-level package to **`zod@3.25.76`** — within the declared range.
2. **Exact Zod requirements of TanStack/Lovable tooling:** only three packages carry a genuine (non-dev) `zod` dependency: `@tanstack/router-generator@1.167.17`, `@tanstack/router-plugin@1.168.18`, and `@tanstack/start-plugin-core@1.171.18` — each declares `"zod": "^4.4.3"` in its real `dependencies`. (`@tanstack/react-router` also references `zod: ^4.4.3`, but only inside its own **`devDependencies`** — used solely when TanStack develops/tests that package itself, never installed as a consumer. `@tanstack/react-start` and `@lovable.dev/vite-tanstack-config@2.7.7` reference no `zod` at all.)
3. **Where `.prefault()` is called:** exclusively inside the compiled output of the three build-tooling packages above (`schema.js`/`schema.ts` in `@tanstack/start-plugin-core`, and their nested zod v4 test fixtures) — a Zod v4-only API used for those packages' own internal config-schema validation during dev/build. **Zero occurrences in `src/`.**
4. **Compatibility of `@lovable.dev/vite-tanstack-config@2.7.7` with the resolved graph:** fully compatible. It declares no `zod` constraint of its own, and a correct install (§5) resolves the three genuinely zod-v4-dependent tooling packages into **isolated nested `node_modules` copies** of `zod@4.4.3`, entirely separate from the top-level `zod@3.25.76` the application itself uses. This is bun's standard, correct behavior for an incompatible nested version range — not a conflict.
5. **Whether the prior `prefault` failure came from an unauthorized Lovable `2.9.0` tooling state instead:** repository evidence contains no trace of a `2.9.0` tooling version anywhere outside `instruction1.47.md` itself, so this cannot be confirmed or refuted from repository history. What **can** be confirmed: the canonical graph, at the authorized `@lovable.dev/vite-tanstack-config@2.7.7`, exhibits no `zod`/`prefault` conflict once the lockfile is correctly regenerated (§5) — a full production build, dev-server startup, and the complete test suite all ran clean with zero `prefault`-related error. This makes an unauthorized/different Lovable tooling state (or an install attempted against the still-broken frozen lockfile, which can produce inconsistent partial resolution) a substantially more likely explanation than any defect in the canonical, authorized dependency graph itself.
6. **Whether any correction beyond the lockfile integrity repair is necessary:** **No.** No Zod change, no TanStack change, no Lovable tooling change is required or recommended.
