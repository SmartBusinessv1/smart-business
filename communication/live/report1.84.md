### 4.6 Disclosed limitation: `delete_catalog_product` / import-row FK interaction

One consequence, not previously surfaced in any prior review: a product that has ever been referenced by an import batch row cannot be hard-deleted via the existing, unmodified `delete_catalog_product` command without first satisfying this FK — `delete_catalog_product`'s own dependent-history pre-check (four existing event tables) does not examine these new tables, and this migration does not alter that command (outside this instruction's authorized scope — no signature/authority change to an existing command without separate authorization, per instruction1.77.md §4). The practical effect is a raw foreign-key-violation database error instead of the command's usual clean `DEPENDENT_HISTORY_CONFLICT` rejection, in this one narrow case. Archiving an imported/matched product is entirely unaffected. Documented in the migration file's own header comment as well.

## 8. Disclosed Implementation Decisions (gaps the locked spec left open)

The EIS is exact about the schema, grants, RLS, claim mechanism, and every field-level rule, but a small number of orchestration-sequencing questions were not explicitly locked. Each is disclosed here rather than silently decided, consistent with this mission chain's established discipline.

1. **Multi-command-per-row idempotency for price/tax/cost.** §45.5.5 locks one idempotency key per row, reused for `create_catalog_product`. It does not address the follow-up `record_catalog_selling_price_change`/`record_catalog_tax_change`/`record_catalog_reference_cost_change` calls a row with those fields also needs. Resolved by deterministically deriving a distinct RFC 4122 UUIDv5 key per `(row_idempotency_key, operation)` pair (`src/lib/catalog-import/idempotency.ts`) — stable across retries, no new dependency, no new persisted column.
2. **Row terminal status when a follow-up command fails.** A row is marked `CREATED` as soon as `create_catalog_product` succeeds (matching §45.5.2's own definition of `resolved_product_id`); a subsequent price/tax/cost command failure is reported as a distinct `warnings` entry in the commit outcome, never silently dropped and never used to mark an already-real product's row `FAILED` (which would make it confusingly retryable while the product already exists).
3. **Category resolution/creation during import.** §7/§9 list Category as a recognized field but do not specify whether an unmatched label is an error or an auto-create. Resolved by applying §21's already-locked archived-conflict rule to the import path (truthful conflict, never silent reuse) and, for a genuinely new label, creating it via the existing governed `create_catalog_category` command at commit time — the same command path an interactive "Create new category" action already uses, never a raw table write, never a new command.
4. **"Skip this row" persistence.** §10 names `Skip this row` as a POSSIBLE_MATCH/NEEDS_CORRECTION decision option but the three locked server functions don't name a dedicated mutation for it. Resolved by accepting an optional `skipRowNumbers` array in `catalogImportCommit`'s existing input, applied via the same server-only bookkeeping client before the claim/create loop — no new server function, no new write boundary.
5. **"Correct the import row and retry."** Implemented as re-uploading a corrected file as a new batch (already explicitly permitted at any time, §13), not as in-place field editing of a persisted row. Building a bespoke partial-row-edit UI was judged out of proportion to the remaining Build Now scope and risked becoming exactly the kind of "bespoke aggregation layer" §10 already rejected for the product-update case; re-upload is simpler, already-safe, and already-locked as always-available.

None of these decisions add a Catalog command, touch Product Truth, weaken RLS/grants, or expand service-role usage. All are reversible, additive UI/orchestration choices within Build Mode's normal discretion.

## 9. Unresolved Defects / Limitations

### 9.1 EIS §37/§45.15's assumed direct-handler-invocation test architecture does not hold in this TanStack Start version

The EIS locked: "the thin `createServerFn` wrapper ... is integration-tested by importing and invoking its exported handler directly in a test module ... no live HTTP server or browser is required." This was tested directly and found not to work as specified, for a concrete, verifiable reason: `requireSupabaseAuth`'s `getRequest()` call needs an active H3-event `AsyncLocalStorage` context — reproducible outside a real request via the framework's own `requestHandler` helper (`@tanstack/start-server-core/request-response`) — but `createServerFn`'s own internal middleware executor additionally requires a *second*, separate "Start context" (`@tanstack/start-storage-context`), which is established only by the compiled app's actual `createStartHandler` entry point, not by any public, documented API reachable from a standalone test module. This is exactly the integration risk the EIS itself flagged in §45.1 ("Phase 2/3 implementation must budget for discovering integration issues with this execution surface that no prior SB-P-1.11 mission has encountered") — confirmed, isolated, and disclosed rather than worked around with an unstable reach into framework internals.

**Consequence:** the server-function layer specifically (auth-middleware wiring + `FormData` handling + orchestration, as opposed to the pure logic it calls and the database contract it writes to) has no committed automated test. In its place: full automated coverage of the pure logic (§6.1), full automated coverage of the exact database contract the server function depends on including the real concurrency race (§6.1), and a real running-server smoke test confirming the module loads and the route renders correctly end-to-end (§7). Genuine gap: an authenticated, real-HTTP exercise of `catalogImportPreview`/`catalogImportCommit`/`catalogImportGetBatch` themselves.

**Recommendation:** a follow-up, separately-scoped Build Mode task to establish a live-dev-server-based test harness (start `vite dev`, sign in a real test user, issue real `fetch` calls to the compiled server-function endpoints) — a larger, different piece of test infrastructure than §37 assumed, not a quick fix.

### 9.2 `vitest.config.ts` alias fix

While building the (ultimately not fully achievable, per §9.1) server-function test, a pre-existing, unrelated gap was found and fixed: `tests/**` could not resolve `@/*` for *value* imports (only for `import type`, which is erased before resolution runs — every prior test file only ever used the alias that way). Fixed with a standard `resolve.alias` entry in `vitest.config.ts`, additive and low-risk; it does not change how any existing test resolves anything, since none of them previously depended on value-import alias resolution working.

### 9.3 Compressed-decompression-bomb defense is a declared-size check, not a streaming byte-counter

EIS §45.3 asks for the 25 MB decompressed-size bound to be "checked incrementally during extraction, not only after full decompression." The implementation sums each ZIP entry's *declared* uncompressed-size field from the central directory before calling `exceljs`'s full load — genuinely rejects the common case, and is what "incremental, pre-full-decompression" concretely means without a byte-counting decompression stream, which `exceljs`'s public API does not expose a hook for. A ZIP crafted with a dishonest (understated) declared size in its central directory could still reach `exceljs`'s own decompression past this check. This is a residual, narrow gap versus a hypothetical fully-instrumented streaming limiter, disclosed rather than overclaimed as closed.

### 9.4 10-second parser wall-clock limit is a post-hoc check, not preemptive cancellation

`papaparse`'s synchronous string-mode API and `exceljs`'s buffer-load API do not expose a mid-parse abort hook reachable from this design without switching to their streaming/worker modes (a larger change than this mission's scope). The limit is enforced by measuring elapsed time immediately after parsing completes and rejecting the result if it already exceeded 10 seconds, rather than aborting a parse in progress at the 10-second mark. For the enforced 5 MB compressed / 25 MB declared-decompressed size caps, a pathological parse is not expected to approach 10 seconds in practice, but this is a real distinction from "the parser is interrupted at 10 seconds," disclosed accordingly.

None of §9.1–§9.4 involve Product Truth, the 19-command boundary, RLS/ACL, or credential exposure — all are implementation-completeness notes about defense-in-depth depth and test-architecture coverage, not open security or correctness defects in what was actually shipped and verified.
