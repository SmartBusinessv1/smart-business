# SB-MIG-1.2A — Lovable OAuth Integration Review (Task 4)

## 1. The Central Finding

The application's Google sign-in path does **not** use Supabase's native OAuth flow. It uses a Lovable-Cloud-specific OAuth proxy, and only hands the *resulting* session to Supabase as a final step. This is a more significant architectural coupling than "the app calls a Lovable wrapper around Supabase OAuth" — it means **Supabase's own Google-provider configuration (client ID, client secret, redirect URIs) may not even be what currently authorizes Google sign-ins in production**, since the actual OAuth handshake with Google is brokered by Lovable Cloud's own service, not by Supabase Auth directly.

## 2. Exact Code Path

- **`src/routes/auth.tsx`**, function `handleGoogle()` (lines 101–120): the sole call site for Google sign-in in the entire application. Calls:
  ```ts
  const result = await lovable.auth.signInWithOAuth("google", {
    redirect_uri: window.location.origin,
  });
  ```
- **`src/integrations/lovable/index.ts`** — explicitly marked `// This file is auto-generated by Lovable. Do not modify it.` Wraps `createLovableAuth()` from the `@lovable.dev/cloud-auth-js` package. Its `signInWithOAuth` implementation:
  1. Delegates the entire OAuth handshake to `lovableAuth.signInWithOAuth(provider, { redirect_uri, extraParams })` — a Lovable Cloud service call, not a Supabase call.
  2. If Lovable's flow performed a full-page redirect (`result.redirected === true`), returns early — the page navigation itself continues the flow.
  3. If Lovable's flow returned tokens directly without a redirect, calls `supabase.auth.setSession(result.tokens)` to install the resulting session into the app's Supabase client.
  4. Only at this final step does Supabase's client library become involved at all.

**No other file in the repository references Google OAuth, `signInWithOAuth`, or the `@lovable.dev/cloud-auth-js` package** — this is a fully contained, single-function integration point, not a diffuse dependency.

## 3. Does the Email/Password Path Share Any of This?

**No.** `src/routes/auth.tsx`'s email/password handlers (`supabase.auth.signInWithPassword`, `supabase.auth.signUp`, `supabase.auth.resetPasswordForEmail`) call the Supabase client directly, with no Lovable involvement anywhere. The password-reset landing page (`src/routes/reset-password.tsx`) is likewise pure Supabase Auth (`onAuthStateChange` for the `PASSWORD_RECOVERY` event, then `supabase.auth.updateUser({ password })`). **User 1's entire recreation path (`02-authentication-recreation-plan.md`) is unaffected by this finding.** Only User 2's path (Google OAuth) is coupled to Lovable.

## 4. Minimum Application Change Required

**Classification: Minimal code change required.**

Not "no change" — the current code cannot function post-Lovable-disconnection, since `@lovable.dev/cloud-auth-js`'s `createLovableAuth()` almost certainly depends on Lovable Cloud's own backend being reachable and configured for this project, which is exactly what a migration away from Lovable removes. Not "authentication redesign" — the change is contained to one function in one file, does not touch session handling, protected-route guards, RLS, or the email/password path at all, and the *user-facing* experience (a "Sign in with Google" button that works) is fully preservable.

**Exact files, and the nature of the intended change (not implemented under this analysis-only task):**

| File | Current state | Intended change |
| --- | --- | --- |
| `src/routes/auth.tsx` | `handleGoogle()` calls `lovable.auth.signInWithOAuth("google", { redirect_uri: window.location.origin })` | Replace with Supabase's native `supabase.auth.signInWithOAuth({ provider: "google", options: { redirectTo: <appropriate post-login URL> } })`. Supabase's native call always performs a full-page redirect (no `result.tokens`/`setSession` branch needed) — the surrounding `try/catch`, busy-state, and error-message handling can likely remain structurally similar, but the specific response shape differs slightly (Supabase returns `{ data, error }`, not `{ redirected, error, tokens }`), so the function body needs adjustment, not just the one call. |
| `src/integrations/lovable/index.ts` | Auto-generated Lovable wrapper; the `signInWithOAuth` export becomes unused once `auth.tsx` no longer calls it | Once no code references it, this file (and the `@lovable.dev/cloud-auth-js` dependency in `package.json`) can be removed entirely — but that removal is itself an application-code change outside this analysis-only task's scope, and outside the "prepare, don't modify" boundary of SB-MIG-1.2A generally. Flagged for the future mission that will actually implement this. |
| `src/integrations/supabase/client.ts` | No change needed | Already the correct, native Supabase client the replacement call would use — no modification required here. |

**This change is explicitly not implemented by this mission** (SB-MIG-1.2A's Task 4 authorizes analysis only; the mission's own boundaries prohibit publishing application changes). It is scoped precisely enough that a future mission could implement and test it as a small, contained, reviewable change — consistent with the Mission Control "minimum-change OAuth parity" decision.

## 5. Consequence for Task 3 (Google OAuth Parity)

Because the current production flow does not exercise Supabase's own Google-provider configuration directly, **this review cannot confirm from application code alone whether Supabase-native Google OAuth is even configured on the Lovable-managed backend today**, let alone on Team LIPS Supabase. Whatever configuration exists (or doesn't) on either project's Supabase Auth settings is independent of what Lovable Cloud's own OAuth app registration for this project has — and this environment has no tool that inspects either. See `03-google-oauth-parity-report.md` for how this uncertainty is handled.
