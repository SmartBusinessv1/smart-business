# SB-MIG-1.1 — Migration Risk Register (Audit 6)

Every risk below is grounded in direct evidence gathered in `01-infrastructure-audit-report.md` and `02-database-comparison-report.md`. No risk here is speculative beyond what is explicitly labeled as such.

Severity scale: **Critical** (blocks migration outright / data-loss or security exposure) · **High** (must be resolved before cutover) · **Medium** (should be resolved before cutover, workable with a documented interim plan) · **Low** (track, resolve opportunistically).

| ID | Risk | Category | Severity | Impact | Recommended Mitigation |
| --- | --- | --- | --- | --- | --- |
| MIG-1 | The idempotency-replay defect fixed under SB-P-1.10-FIX-IDEMPOTENCY-RLS-1.0 (migration #11) is still live in the Lovable-managed production database — confirmed by direct inspection of `create_inventory_movement()`'s function body. | Schema drift / active production defect | **High** | Every retried inventory-movement request in production (matching idempotency key, identical payload) is treated as new rather than gracefully deduplicated — surfaces as a raw constraint-violation error or a misleading "already recorded" error to the caller, not silent data corruption, but a real production-facing failure mode. | Apply migration #11 to the Lovable-managed backend (or to whichever database becomes authoritative) under a separately authorized corrective mission before or as part of cutover. The migration is already written, applied to, and verified against the Team LIPS test project. |
| MIG-2 | Migration #3 (`20260719140000`) exists in the repository's `supabase/migrations/` but has no corresponding entry in the Lovable backend's `supabase_migrations.schema_migrations`, and structurally cannot be re-applied after migration #2 (plain `CREATE TABLE`, no `IF NOT EXISTS`, same table as #2). | Schema drift / migration history integrity | Medium | A naive "replay every file in `supabase/migrations/` in order" migration strategy will fail outright at file #3 against any database that already has #2 applied (including a fresh Team LIPS Supabase once the transactions domain is added). | Before executing any migration replay, explicitly exclude migration #3 (or confirm — manual verification required — that it was intentionally superseded and document why) rather than assuming the file list is safe to run unmodified end-to-end. |
| MIG-3 | Team LIPS Supabase is missing the entire transactions domain (`transactions`, `transaction_correction_events`, `correct_transaction()`, associated triggers and 5 RLS policies) — confirmed by direct schema comparison. | Schema completeness | **High** | Team LIPS Supabase cannot serve as a production target in its current state; any cutover today would silently drop the transactions feature entirely. | Apply migrations #2, #4, #5 (the transactions-domain migrations) to Team LIPS Supabase before it is considered migration-ready. Re-run the full comparison in this report afterward to confirm parity. |
| MIG-4 | `anon`, `authenticated`, and `service_role` all hold full DML privileges (`SELECT/INSERT/UPDATE/DELETE/TRUNCATE/...`) on every application table, on **both** databases — confirmed via `information_schema.role_table_grants`. Enforcement is 100% dependent on RLS policy correctness; there is zero grant-level defense-in-depth. | Security / RLS design | Medium | This matches Supabase's own platform default and is not a regression introduced by either project, but it means any future table added without a complete, correct RLS policy set (including explicit UPDATE/DELETE policies where none is intended) is immediately writable/deletable by any authenticated user, with no grant-layer backstop. This was empirically significant during SB-P-1.10-TESTS-1.0: the "append-only" guarantee for ordinary users turned out to be enforced by RLS's default-deny (no UPDATE policy exists), not by grants or, for ordinary callers, by the triggers. | Before or during Phase 2, consider adopting explicit `REVOKE ALL ... FROM PUBLIC` + narrowly-scoped `GRANT` statements matching each table's intended policy surface, as defense-in-depth beyond RLS. Not required to unblock migration, but reduces blast radius of a future RLS authoring mistake. |
| MIG-5 | Two foreign keys on `inventory_movements` (`inventory_movements_correcting_of_fk`, `inventory_movements_item_business_fk`) have no covering index — flagged by Supabase's own performance advisor on Team LIPS Supabase. | Performance | Low | Slower FK-enforcement checks and cascade/restrict lookups as `inventory_movements` grows. Current row counts (0 in production, 940 in the test project) are far too small for this to matter yet. | Track for a future performance-tuning mission once real movement volume exists; not a migration blocker. |
| MIG-6 | 10 of 16 RLS policies (all 4 policies on `businesses`, all 3 on `inventory_items`, both on `inventory_movements`, both on `inventory_movement_idempotency_keys`) call `auth.uid()`/`current_setting()` directly rather than wrapped in `(select auth.uid())` — flagged by Supabase's `auth_rls_initplan` performance advisor. | Performance | Low–Medium | Each policy re-evaluates the auth function per row rather than once per query; degrades at scale (thousands+ rows per query). Not a correctness issue. | Track as a future RLS-authoring-pattern cleanup. Rewriting RLS policies is itself a schema change requiring its own authorized mission — do not bundle into the migration cutover unless explicitly scoped in. |
| MIG-7 | "Leaked Password Protection Disabled" — flagged by Supabase's security advisor on Team LIPS Supabase (WARN level). Equivalent setting on the Lovable-managed backend is unverified (GoTrue project settings are not queryable via SQL). | Security / Auth configuration | Medium | Users can set passwords that are already known-compromised (per HaveIBeenPwned). | Enable leaked-password protection on whichever project becomes authoritative, and manually verify the current state on the Lovable backend before assuming parity either way. |
| MIG-8 | `SUPABASE_SERVICE_ROLE_KEY` is referenced in application code (`src/integrations/supabase/client.server.ts`) but has no value recorded anywhere in this repository (not in `.env`, `.env.test`, or any example file) — confirmed by the Audit 1 repository sweep. | Environment / secrets migration | **High** | The exact mechanism by which Lovable Cloud currently injects this secret at runtime is not documented in the repository. Cutover risks silently breaking every server-side admin operation if the new environment's equivalent secret isn't provisioned and wired up correctly before go-live. | Before cutover, explicitly identify and document how the current service-role key is injected (Lovable Cloud project secrets), obtain Team LIPS Supabase's own service-role key through its dashboard (never via a shared/committed channel), and configure the new hosting environment's runtime-secret mechanism as an explicit Phase 2 task with its own verification step. |
| MIG-9 | No CI workflow runs the build, `npm run lint`, `npx tsc --noEmit`, or the 62-test Vitest suite. The only CI gate in the repository is a Markdown-only quality check. | Process / repository readiness | Medium | Nothing currently prevents a broken migration file, a failing test, a type error, or a lint regression from being merged to `main` during the migration effort itself — the migration work has no automated safety net beyond manual, on-demand execution. | Add CI workflow(s) — at minimum `npx tsc --noEmit` and `npm run test` on every PR touching `src/`, `tests/`, or `supabase/migrations/` — before or during Phase 2, so migration-related changes get automated verification rather than relying solely on manual runs. |
| MIG-10 | The 62-test automated suite covers the inventory domain exclusively (`tests/inventory/*.test.ts`). The transactions/correction-events domain (`correct_transaction()`, its RLS policies, the audit trail) has **zero** automated test coverage. | Test coverage | Medium–High | Any schema/RLS/function change to the transactions domain during migration (including simply re-applying its migrations to Team LIPS Supabase per MIG-3) has no automated regression detection — correctness would rest entirely on manual verification, the same weaker evidentiary position the inventory domain was in before SB-P-1.10-TESTS-1.0. | Author an automated test suite for the transactions/correction-events domain, following the same pattern established for inventory (dedicated test project, real signed-in sessions, one test file per meaningful obligation), before or during Phase 2 — ideally before migrating that domain's schema to Team LIPS Supabase. |
| MIG-11 | Team LIPS Supabase has zero Google-OAuth identities on record (188 `auth.users`, all `email` provider) — confirmed by direct query. Production has 1 of its 2 real users signed in via Google. | Auth configuration parity | Medium | If Google OAuth isn't configured identically on Team LIPS Supabase (client ID/secret, authorized redirect URLs) before cutover, that real user cannot sign in post-migration. | Manually verify and configure the Google OAuth provider on Team LIPS Supabase to match production before cutover; test an actual Google sign-in against it as part of Phase 2 verification, not just schema/RLS checks. |
| MIG-12 | The application's OAuth sign-in path is implemented through a Lovable-specific integration layer — `src/integrations/lovable/index.ts`, wrapping `@lovable.dev/cloud-auth-js`'s `createLovableAuth()` — rather than calling Supabase's native `supabase.auth.signInWithOAuth(...)` directly. Confirmed by the Audit 1 repository sweep. | Architecture / Lovable dependency | **High** | Disconnecting Lovable (a mission boundary explicitly forbidden in this audit, but presumably a later migration-phase goal) would break Google sign-in entirely unless this layer is replaced first, since it is the sole code path by which OAuth tokens currently reach the Supabase client. | Plan a dedicated Phase 2/3 task to replace `src/integrations/lovable/index.ts`'s OAuth flow with native Supabase `signInWithOAuth`, and test it thoroughly — this is the one authentication path most directly coupled to Lovable's continued availability. |
| MIG-13 | The Lovable project's own published URL is `https://governed-growth-path.lovable.app`. The most recent completion report (`docs/implementation/SB-P-1.10/completion-report.md`) states the runtime is "published at `https://smartbusiness.teamlips.com`." These were not reconciled by this audit. | Documentation / domain configuration | Low | If `smartbusiness.teamlips.com` is a custom domain DNS-mapped onto the Lovable-hosted preview (a standard Lovable feature), disconnecting Lovable could also break that custom domain, not just the `.lovable.app` URL — this audit cannot determine which from schema/database inspection alone. | **Requires manual verification**: confirm the custom-domain mapping (or lack thereof) via the Lovable dashboard and DNS records before any Lovable-disconnection step in a later migration phase. |
| MIG-14 | Edge Functions and Storage buckets on the Lovable-managed backend could not be enumerated via any tool available in this environment (only confirmed absent on Team LIPS Supabase and absent from the repository). | Discovery completeness | Low | Low probability given no repository trace and no Storage/Edge-Function client code anywhere in `src/`, but not a confirmed zero. | **Requires manual verification** via the Lovable or Supabase dashboard for project `wwgqnshcgbukqczqblsm` before treating "no Edge Functions, no Storage" as fully confirmed rather than "no evidence found." |

No risk in this register is rated Critical: nothing found blocks migration outright or represents an active, unrecoverable data-loss or security-exposure condition. The four High-severity items (a known, already-fixed-but-undeployed defect; a materially incomplete schema on the migration target; an undocumented secret-injection dependency; and an architectural Lovable coupling in the OAuth path) are all addressable with scoped, already-understood work — none require new discovery to resolve, only authorized execution.
